# Сервер обрывает соединение на любом PATCH-запросе

**Приоритет:** блокер
**Хост:** `http://176.123.162.135:8081`
**Проверено:** 21.09.2026, воспроизводится стабильно
**Затронуто:** iOS и Android, все сборки приложения

---

## 1. Симптом

Любой PATCH-запрос по любому маршруту завершается закрытием соединения без ответа.
TCP-соединение устанавливается нормально (~4 мс), затем сервер держит его около
390 мс и закрывает, не отправив ни байта.

```
$ curl -v -X PATCH http://176.123.162.135:8081/me -d '{}'
*   Trying 176.123.162.135:8081...
* Connected to 176.123.162.135 port 8081
> PATCH /me HTTP/1.1
> Content-Type: application/json
> Content-Length: 2
* Empty reply from server
curl: (52) Empty reply from server
```

То же самое через сырой сокет — получено ровно 0 байт:

```
$ printf 'PATCH /config HTTP/1.1\r\nHost: 176.123.162.135:8081\r\nConnection: close\r\n\r\n' \
    | nc 176.123.162.135 8081 | wc -c
0
```

В мобильном приложении это выглядит как `Network request failed`: системный HTTP-клиент
не отличает обрыв соединения от потери сети, поэтому пользователь видит «нет связи
с сервером» при полностью рабочем интернете.

---

## 2. Что из-за этого сломано

Всё, что в API использует PATCH. Критичнее всего первый пункт: новый покупатель
физически не может завершить регистрацию и попасть в приложение.

| Эндпоинт | Что не работает |
|---|---|
| `PATCH /me` | Завершение регистрации покупателя — **вход в приложение невозможен** |
| `PATCH /me` | Редактирование профиля (имя, фото) |
| `PATCH /me/shop` | Редактирование магазина продавца (название, описание, фото) |
| `PATCH /products/{id}` | Редактирование объявления |
| `PATCH /products/{id}/images/{imageId}` | Изменение порядка фотографий |

Флоу продавца работает только потому, что целиком построен на POST
(`/auth/seller/accept-invite`, `/auth/seller/complete`). Покупатель упирается
в PATCH сразу на последнем шаге регистрации.

---

## 3. Локализация: отбрасывание происходит выше приложения

Ключевое наблюдение. Запрос `DELETE /me` возвращает корректный `405`, и в заголовке
`Allow` роутер сам перечисляет методы, зарегистрированные на этом маршруте:

```
$ curl -i -X DELETE http://176.123.162.135:8081/me
HTTP/1.1 405 Method Not Allowed
Allow: PATCH          <-- роутер знает про PATCH
Allow: GET
X-Request-Id: 3d24fe2d461023d3f7820173a8676fdd
```

То есть приложение знает про `PATCH /me` и готово его обработать, но сам PATCH-запрос
до него не доезжает. Значит, запрос отбрасывается **до роутинга**.

Подтверждается поведением на несуществующем маршруте: `POST /nonexistent` отдаёт
честный `404 page not found`, а `PATCH /nonexistent` так же молча обрывается.
Если бы дело было в панике конкретного хендлера, до 404-й ветки роутера запрос
бы доходил.

### Срез по методам

Проверялись `/config` (публичный) и `/me` (требует токена). Результат одинаков на обоих
и не зависит от наличия тела запроса, версии HTTP (1.0 / 1.1) и регистра имени метода.

| Метод | Ответ | Вердикт |
|---|---|---|
| GET | 200 / 401 | норма |
| HEAD | 405 `Allow: GET` | норма |
| POST | 405 / 404 | норма |
| PUT | 405 | норма |
| DELETE | 405 `Allow: PATCH, GET` | норма |
| OPTIONS | 405 | норма |
| **PATCH** | — (0 байт, ~390 мс) | **обрыв** |
| **TRACE** | — (0 байт, ~390 мс) | **обрыв** |
| **PROPFIND** | — (0 байт, ~390 мс) | **обрыв** |
| **FOOBAR** (несуществующий метод) | — (0 байт, ~390 мс) | **обрыв** |

**Вывод.** Работают ровно `GET`, `HEAD`, `POST`, `PUT`, `DELETE`, `OPTIONS`.
Всё остальное, включая PATCH, обрывается. Это не сбой на конкретном методе,
а **белый список методов**, из которого PATCH просто забыли.

## 4. Где искать

Закрытие соединения без ответа — характерная подпись nginx-директивы `return 444`.
Типовой сниппет «хардненга», дающий ровно такую картину:

```nginx
# PATCH отсутствует в списке
if ($request_method !~ ^(GET|HEAD|POST|PUT|DELETE|OPTIONS)$) {
    return 444;   # закрыть соединение без ответа
}
```

Проверить всю цепочку перед приложением, сверху вниз:

1. Внешний балансировщик / WAF / антиDDoS-прокси, если он есть перед хостом.
2. nginx или другой реверс-прокси: директивы `limit_except`, `if ($request_method …)`,
   `return 444`, а также ModSecurity и подобные модули с собственным списком
   разрешённых методов.
3. Глобальный middleware Go-приложения, выполняющийся до роутера, который может делать
   `panic`, `Hijack()` или закрывать соединение на неизвестном методе.
   Признак, что это **не** он: у отброшенных запросов нет заголовка `X-Request-Id`,
   который проставляется всем остальным ответам — значит, до request-id middleware
   запрос тоже не доходит.

Стабильная задержка ~390 мс перед закрытием (при RTT в 4 мс) выглядит как фиксированный
таймаут или отдельная стадия обработки, а не как мгновенный отказ роутера — ещё один
довод в пользу промежуточного звена.

---

## 5. Что нужно сделать

- Разрешить метод `PATCH` на всей цепочке до приложения, чтобы запрос доходил
  до Go-роутера, который его уже поддерживает.
- Проверить, что на неподдерживаемый метод сервер отвечает честным `405` с заголовком
  `Allow`, а не рвёт соединение: обрыв неотличим от сетевой аварии и на клиенте всегда
  выглядит как «нет интернета».
- Если белый список методов нужен как мера защиты — оставить его, но с `return 405`
  вместо `444` и с PATCH внутри списка.

Со стороны мобильного приложения обходного пути нет: `X-HTTP-Method-Override: PATCH`,
`X-Method-Override` и `?_method=PATCH` поверх POST сервер отдаёт как `405` —
эти заголовки на нём не обрабатываются.

## 6. Критерии приёмки

Все проверки — с любой внешней машины, без VPN и без туннелей.

1. `PATCH` на несуществующий маршрут возвращает `404`, а не обрывается:
   `curl -i -X PATCH $HOST/nonexistent -d '{}'`
2. `PATCH /me` без токена возвращает `401` с JSON-телом, как это делает `GET /me`:
   `curl -i -X PATCH $HOST/me -H 'Content-Type: application/json' -d '{}'`
3. `PATCH /me` с валидным токеном и телом `{"display_name":"Тест"}` возвращает `200`
   и обновлённого пользователя.
4. Ответ `PATCH /me` содержит **полное** представление пользователя — обязательно
   с полями `id`, `role` и `is_admin`. На `role` в приложении держится вся ролевая
   развилка интерфейса.
5. `PATCH /me/shop` и `PATCH /products/{id}` отвечают `200` на валидный патч.
6. Все ответы несут заголовок `X-Request-Id` — признак того, что запрос прошёл
   общий middleware.

## 7. Смежные находки

### 7.1. POST /products игнорирует поле images

Приложение передаёт массив `images` прямо в теле создания товара, но объявление
возвращается без них. Подтверждено данными с продакшена:

```
$ curl $HOST/products/5d3a091a-ab46-44b1-9530-be0af7ebfd39
{
  "id": "5d3a091a-…", "title": "Restart", "status": "active",
  "images": [],
  "thumbnail_url": null
}
```

Для покупателя такое объявление выглядит пустой карточкой без фото. Нужно либо
применять `images` при создании, либо явно задокументировать, что фотографии
регистрируются только отдельным `POST /products/{id}/images`. В приложении на этот
случай уже добавлен фоллбэк, но он маскирует проблему, а не решает её.

### 7.2. POST /conversations вернул 403 покупателю — требует проверки

Покупатель на карточке чужого активного товара получил
`403 "you do not have permission to do this"` при попытке открыть чат.
Воспроизвести со стороны фронтенда не удалось — нет тестового токена покупателя.

Просьба описать точное правило доступа к `POST /conversations`: какие роли допускаются
и при каких условиях владельцу/не-владельцу выдаётся 403. Не исключено, что аккаунт
в этом случае был продавцом и отказ корректен, но правило нужно зафиксировать, чтобы
приложение скрывало кнопку заранее, а не узнавало об отказе постфактум.

### 7.3. Тексты ошибок

Просьба ко всем 4xx: отдавать `detail` в том виде, в каком его можно показать
пользователю, либо стабильный машиночитаемый `code`. Сейчас в интерфейс прилетает
английская строка `you do not have permission to do this`.
